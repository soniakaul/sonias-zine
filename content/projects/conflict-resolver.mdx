The first time I watched an NX-OS engineer walk through a branch-collapse merge by hand, I started counting. By minute forty he had resolved nine of eighty-three conflicting files. Second monitor on the ticket, third on the diff, yellow legal pad with arrows on it. The arrows were the giveaway. When the tool you reach for is a legal pad, the tooling has lost.

The Conflict Resolver started as one question: what if the engineer&rsquo;s role wasn&rsquo;t to do the merge, but to *approve* the merge? The merge itself is something an LLM can reason about cleanly. The thing humans add isn&rsquo;t pattern matching; it&rsquo;s judgment about context that lives outside the diff.

## The architecture

```
codedrop trigger
       │
       ▼
  git_conflicts_scan.pl  ───►  spawns background agent
                                       │
                                       ▼
                              python orchestrator
                                       ├──► Codex CLI (per file)
                                       ▼
                              audit_log.json
                                       ▼
                              Node.js UI
                                       ▼
                              apply_resolution.py
```

V1 is live in production. 500+ conflicts resolved end-to-end so far, every decision auditable, every resolution reversible. The current focus is the quality of recommendations and the context engineering that surrounds them — the boring work that decides whether engineers trust the system enough to lean on it.

## V2: confidence-calibrated recommendations

V2 layers an AI recommendation alongside each engineer decision — confidence score, one-sentence explanation, citation back to the part of the file that justified it. Engineer scans, overrides the wrong ones, approves the rest. Every override becomes structured signal.

The open problem is confidence calibration. A model that says &ldquo;92% sure&rdquo; needs to be wrong 8% of the time, no more and no less, or the engineers stop trusting the number — and once they stop trusting the number, they start re-reading every recommendation, and the loop is broken.

## V3: the override stream as learning data

V3 turns the override stream into the most valuable artifact in the system. Each override is a labeled disagreement between the model and a senior engineer on a real, production-scale conflict — exactly the kind of supervision signal that&rsquo;s expensive to manufacture and almost impossible to fake. V3 feeds these insights back into the model as in-context learning examples, then eventually as fine-tuning data. The goal: a resolver whose calibration improves the more it&rsquo;s used.
